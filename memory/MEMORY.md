# MEMORY — AkunCalcu

- El sistema de permisos quedó centralizado en `akuna_calc/usuarios/access_control.py`, usando códigos de acceso y mapeo por `namespace:url_name`.
- Los perfiles de acceso viven en `PerfilAccesoUsuario` y los roles globales en `RolSistema`; la migración `usuarios/0002_seed_admin_role.py` asegura el rol `Admin`.
- Si se agregan nuevas vistas o APIs que deban respetar permisos, hay que registrarlas en `ACCESS_MODULES` y/o `ROUTE_ACCESS_MAP` para mantener alineados sidebar, login y bloqueo por URL.
- El estándar actual de selects vive en `akuna_calc/core/templates/core/base.html` a través de `window.AkunSelect2`; para nodos dinámicos usar `reinit` o `refresh`, y para modales declarar `data-select2-dropdown-parent`.
- `no-select2` quedó reservado para micro-selects inline donde el buscador rompe una UI compacta; no usarlo en formularios o filtros generales.
- En `presupuestos.Presupuesto` existe `modalidad_sena` con choices cerrados (`50_50`, `70_30`) y default `50_50`; se configura desde el panel lateral de `presupuestos/detalle.html` debajo de `tipo_obra`.
- Visor 3D de aberturas en el cotizador de presupuestos (FEAT-030 / ADR-015): `static/js/viewer3d.js` (Three.js puro, ESM autocontenido, `window.AkunViewer`), cargado perezosamente en `presupuestos/detalle.html` vía import map + `window.__loadAkunViewer`. La tipología se deriva en el backend con `pricing/tipologia.py::clasificar_tipologia(descripcion, cantidad_hojas)` y se expone en `ProductosListView` + `api_get_producto` (`tipologia` + `cantidad_hojas`). Sin build, sin migración. **Ojo:** `style={{}}` de JSX rompe el parser de Django → usar clases Tailwind. Fase 2 pendiente: PNG por ítem en lista + PDF.
- Estructuras (FEAT-045 / REQ-062 Etapa 1 / ADR-022): una estructura es UN `ItemPresupuesto` con `resultado_json['tipo']='estructura'` (sin modelo ni migración); servicio `pricing/services/estructura.py`, editor `presupuestos/_estructura_editor.html` + `static/js/estructura.js`. La geometría está duplicada en Python y JS con `fixtures_estructura_geometria.json` compartido (`audit_estructura.mjs`). Al confirmar genera una orden por módulo (M1..Mn) con numeración corrida. Sin probar con el catálogo real; Etapa 2 pendiente.
- Asistente de clientes (REQ-075 / FEAT-058 / ADR-032): app `agente`, menú «Agente» en Operación. `ConfiguracionAgente.obtener()` es un registro único (pk=1) con firma, tono, modelo de IA (`gpt-5-mini`), canales (arrancan apagados), modo prueba y números permitidos; además `FranjaAtencion`/`DiaCerrado` (horario), `TecnicoVisita` + `FranjaTecnico` + `ZonaTecnico` (visitas) y `EntradaConocimiento`. Etapa 1a hecha (solo configuración); la 1b agrega conversaciones, APIs para n8n y el router del webhook de Meta, que hoy comparte número con Gastos/Agenda/Resumen.
- Motor de conversación del agente (FEAT-059 / ADR-033): vive en Django, no en n8n. `agente/motor.py::responder(conversacion, texto)` arma el contexto (config, canal, horario de `agente/horario.py`, conocimiento activo, últimos 30 mensajes), llama a OpenAI vía `agente/openai_cliente.py::pedir_json` (urllib, `OPENAI_API_KEY`, 25 s, JSON schema estricto) y guarda `Mensaje`s con el detrás de escena en `detalle`. `Conversacion.es_simulacion` separa el simulador (Agente → Simulador) de los canales reales. En los tests se mockea `agente.motor.openai_cliente.pedir_json`.
